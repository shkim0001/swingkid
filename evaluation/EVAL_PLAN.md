# SwingKid 평가 계획

> 9일차 「4. 평가」(4-1 평가 기준 · 4-2 평가 실행 · 4-3 개선 확인 · 4-4 RAG 평가 지표)를 이 프로젝트에 맞춘 계획입니다.
> **(제안)** 표시는 아직 정하지 않은 값입니다. 첫 라이브 실행 뒤 숫자를 보고 확정합니다.

## 1. 목적

- **회귀를 배포 전에 잡는다.** 프롬프트·가드레일·검색 설정을 바꿀 때마다 같은 평가셋을 돌려, 되던 것이 안 되는지 확인합니다.
- **개선은 감이 아니라 전후 비교로 증명한다.** 점수 한 번이 아니라 "수정 전 → 수정 후"를 같은 잣대로 비교합니다.
- **실패하면 어디를 고칠지 알게 한다.** 통과·실패만이 아니라 검색 문제인지 답변 생성 문제인지, 무엇이 빠졌는지까지 남깁니다.

## 3. 평가 구성: 세 겹

| 겹 | 무엇을 | 어떻게 | 언제 | 비용 |
|---|---|---|---|---|
| **A. 정답셋 기반 (코드)** | status · issue_codes · sources · agents · trace 단계 · 고정 문구 | 지금 `src/evaluate.py` 그대로 (오프라인 + 라이브) | 모든 변경 | 오프라인 무료 |
| **B. LLM 심사** | 답변이 질문에 맞게, 근거 안에서, 금지 항목 없이 답했는가 (수동 확인 46개 포함) | 고정 루브릭 judge (4-1 원칙) | 라이브 실행 때 | Bedrock 호출 |
| **C. RAG 진단 지표** | 실패 원인이 검색인가 생성인가 | RAGAS 4지표를 직접 계산 (라이브러리 설치 없이) | 라이브 실행 때 + 검색 설정을 바꿀 때 | 일부 호출 |

### A. 정답셋 기반 평가 (코드)

이미 있는 자동 채점을 그대로 씁니다. 답이 하나로 정해지는 항목만 맡습니다.

- `status=answered|no_answer|blocked`, `issue_codes` (문제 코드·`guard_` 코드), `sources`에 기대 문서·URL 포함
- `agents`에 기대 sub-agent 포함, `trace`에 기대 단계 포함, 금지 단계(예: 무관 질문에서 검색·LLM 호출) 없음
- 고정 문구 (근거 없음·차단·재촬영 안내)

추가할 것: **라이브 모드 실행** `python -m src.evaluate --live`. 같은 평가셋을 실제 부품으로 돌려, 오프라인에서는 못 잡는 문제(라이브 검색기의 근거 누락, MCP 웹 검색 시간 초과, MediaPipe 판정 흔들림)를 봅니다.

### B. LLM 심사 (LLM-as-a-Judge)

4-1의 네 원칙을 그대로 지킵니다.

| 원칙 | 이 프로젝트에서 |
|---|---|
| 고정 루브릭 | 아래 5·3·1점 기준을 상수로 고정. "길이가 아니라 정확성으로" 명시 |
| 같은 모델·파라미터 | `JUDGE_MODEL = Claude Sonnet 4.5 (us)`, `temperature=0`, 상수로 고정. 버전 비교는 항상 같은 judge로 |
| 편향 주의 | 길이 편향: 루브릭에 명시. 위치 편향: 두 답을 나란히 비교할 때(4-3 전후 비교)는 A/B 순서를 바꿔 두 번 보고 일치할 때만 인정 |
| 사람이 최종 확인 | judge 는 초벌 채점. 낮은 점수·애매한 판정은 사람이 검토 목록으로 확인 |

**입력**: 질문 · 모델 답변 · 근거(contexts) · 기대 특성(`expected_traits`) · 금지 항목(`forbidden`)
→ 정답 문장이 따로 없으므로 `expected_traits`가 정답(reference) 역할을 합니다.

**출력** (구조화 출력):

```python
class JudgeResult(BaseModel):
    score: int = Field(ge=1, le=5)
    is_correct: bool            # 기대 특성의 핵심을 의미상 충족하는가
    missing: list[str]          # 빠진 기대 특성 → 무엇을 고칠지
    violations: list[str]       # 어긴 금지 항목 (지어낸 수치·브랜드 추천·의학 진단 등)
    grounded: bool              # 답변의 주장이 모두 contexts 안에 있는가 (아래 Faithfulness)
    reasoning: str
```

**루브릭 (초안)**:

```
길이가 아니라 정확성으로 판단하세요.
5점: 질문에 직접 답하고, 기대 특성을 모두 충족하며, 모든 내용이 근거 문서 안에 있고, 금지 항목이 없다
4점: 핵심은 충족했지만 기대 특성 하나가 약하거나 덜 쉽게 설명했다
3점: 관련은 있지만 기대 특성 일부가 빠졌거나 장황하다
2점: 일부만 맞고 근거 밖 내용이 섞였다
1점: 질문에 답하지 않거나, 사실이 틀리거나, 금지 항목을 어겼다
```

**대상과 예외**

| 응답 | judge 가 보는 것 |
|---|---|
| answered (텍스트·사진·영상·웹) | 위 루브릭 전체. 사진·영상은 "측정 각도와 교육용 기준값을 먼저 말했는가", 웹은 "조회 날짜·출처 차이를 밝혔는가" 포함 |
| no_answer · blocked | judge 안 함. 고정 문구라 A(코드)로 충분 |
| 최신 정보 (예: 올해 LPGA 순위) | 정답이 날마다 바뀌므로 정답 비교 대신 **grounded(출처에 있는 내용만 말했는가)**만 봄 |

**안정성 확인**: 같은 (질문·답변·근거)를 두 번 채점해 같은 점수가 나와야 합니다(4-1 확인 기준). 다르면 3회 채점 후 다수결로 정하고, 해당 문항을 사람 검토 목록에 올립니다.

**사람 검토 목록**: score ≤ 3 · `is_correct=false` · `violations` 있음 · 두 번 채점 불일치. 결과 파일에 따로 모아 사람이 보고 "판정 맞음/틀림"을 적습니다.

**주의 — 같은 계열 채점**: 코칭 모델과 judge 가 모두 Claude 라 judge 가 같은 계열의 답을 후하게 볼 수 있습니다. 점수는 절대 기준이 아니라 **같은 judge 로 본 버전 간 상대 비교**로만 해석합니다(4-1).

### C. RAG 진단 지표 (RAGAS 4지표를 직접 계산)

RAGAS 는 설치하지 않고, 이미 있는 값과 judge 로 같은 질문에 답합니다.

| 지표 | 질문 | 이 프로젝트에서 계산 | 낮을 때 손볼 곳 |
|---|---|---|---|
| Context Recall (검색 재현율) | 필요한 문서를 가져왔나 | 기대 문서가 `sources`에 있는 비율 (코드) | `TOP_K`, 청크 크기, 하이브리드 검색 기준값 |
| Context Precision (검색 정밀도) | 관련 문서가 위에 있나 | 기대 문서의 순위 → 1위 비율 · MRR (코드) | BM25 점수·단어 비율 기준, Chroma 관련도 하한 |
| Faithfulness (충실성) | 근거 밖 내용을 지어내지 않았나 | judge 의 `grounded` · `violations` | coach 시스템 프롬프트 "근거 밖 내용 금지" 강화 |
| Answer Relevancy (답변 적합성) | 질문에 바로 답했나 | judge 점수 중 '질문에 직접 답함' 판단 | 프롬프트의 답변 형식·길이 규칙 |

검색 지표는 평가셋 20건만으로는 작으므로 **`data/calibration.json` 50문항(평가셋과 별개)**을 함께 씁니다. 평가셋에만 맞춰 고치는 과적합(4-3 함정)을 막는 역할도 합니다.

## 4. 실행 방법 (4-2)

| 명령 | 내용 | 시간·비용 (제안) |
|---|---|---|
| `python -m src.evaluate` | A. 오프라인 코드 채점 (지금 있음) | 수 초, 무료 |
| `python -m src.evaluate --live` | A. 라이브 코드 채점 | 20문항 × 실제 그래프 ≈ 3~5분 |
| `python -m src.evaluate --live --judge` | A + B + C. answered 답변을 judge 로 2회 채점 | Bedrock 호출 약 20(코칭) + 2×answered(심사) 회 |
| `python -m src.calibrate --live` | C. 라이브 검색기로 검색 지표 | Titan 임베딩 50회 |
| `python -m src.evaluate --live --judge --save --label v2 --compare evaluation/results/<v1>.json` | 전후 비교(4-3) | 위와 같음 |
| `... --strict-model` | 코칭 모델 대체 경로 끄기(회차 비교용, 4차부터) | 같음 |
| `python -m src.evaluate --set evaluation/guardrail_stress.csv [--live --judge]` | 가드레일 스트레스 세트 18건 | 오프라인 수 초 |

결과는 `evaluation/results/<날짜>_<버전>.json` 으로 남깁니다(문항별 판정·답변·근거·judge 결과·지표). 화면 출력은 유형별 요약 + 실패·검토 대상만.

**평가셋 분리 규칙**: 알 수 없는 category 나 형식이 어긋난 조각은 채점에서 빼서 따로 보여 줍니다(지금도 '수동 확인'으로 분리). 조용히 통과시키지 않습니다.

## 5. 개선 확인 · 회귀 (4-3)

1. 결과에서 FAIL·검토 대상을 봅니다.
2. 문항마다 원인을 가릅니다: **모델(에이전트)이 틀렸나, 판정이 못 알아봤나.**
   - 판정이 틀렸으면 채점 규칙을 고치되, 왜 고쳤는지 HISTORY.md 에 남깁니다. 판정을 느슨하게 해서 엉뚱한 답까지 통과시키지 않습니다.
   - 모델이 틀렸으면 판정은 그대로 두고 에이전트(프롬프트·라우팅·검색)를 고칩니다.
3. 같은 평가셋을 다시 돌려 **전후 비교표**를 남깁니다. 고친 문항이 통과하고 **나머지가 그대로 통과하는지(회귀)** 함께 봅니다.

   ```
   수정 전: 코드 18/20 · judge 평균 3.9 · is_correct 80% · 위반 1건
   수정 후: 코드 20/20 · judge 평균 4.2 · is_correct 90% · 위반 0건   (나머지 유형 변화 없음)
   ```
4. **실패했던 문항은 고친 뒤에도 지우지 않습니다.** 같은 버그의 재발을 막는 회귀 테스트가 됩니다.
5. 평가셋에만 맞춰 고치지 않았는지 `calibration.json` 과 평가셋 밖 질문 몇 개로 확인합니다.

|---|---|---|
| 오프라인 코드 채점 | **20/20** | 지금 달성. 모든 변경에서 유지 |

## 8. 위험과 한계

- **같은 계열 judge**: 위 3-B 참고. 상대 비교로만 해석하고 사람 검토로 보완합니다.
- **웹 검색은 매번 결과가 다름**: DuckDuckGo 결과·시간 초과가 실행마다 달라 info_agent 문항은 흔들립니다. 실패 원인을 '웹 검색 실패'로 따로 집계하고, 회귀 판단에서는 분리해 봅니다.
